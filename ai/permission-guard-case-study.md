# Codex Permission Guard 셸 인용 우회 보완

## 문제

DevChat의 Codex `PreToolUse` Guard는 `git reset --hard`처럼 사용자 변경을 폐기할 수 있는 명령을 실행 전에 차단한다. 초기 구현은 원본 명령 문자열에서 위험 옵션을 찾는 방식이었다.

셸은 붙어 있는 인용 조각을 하나의 인자로 합친다. 따라서 아래 명령은 Git에 `--hard` 옵션을 전달한다.

```sh
git reset --h''ard
```

하지만 초기 Guard는 문자열에 `--hard`가 연속해서 나타날 때만 차단했다. 이 명령은 Guard를 통과했고, 검증용 읽기 전용 샌드박스가 Git 쓰기를 막았다. Guard 자체가 위험 작업을 거부한 것은 아니었다.

## 원인

정책 판정이 셸의 인자 경계가 아니라 원본 텍스트에 의존했다. 셸이 실행 전에 인용을 제거하고 인자를 결합한다는 점이 탐지 단계에 반영되지 않았다.

## 해결

`guard_policy.py`에서 Bash ANSI-C 인용을 실행 없이 해석한 뒤 `shlex.split`으로 토큰화하고, 다시 공백으로 연결한 정규화 문자열을 정책 검사에 사용했다. 이 변경으로 다음 표현도 각각 동일한 위험 옵션으로 판정한다.

```sh
git reset --h''ard
git push --fo''rce origin main
git add -''A
git reset --h$'\x61'rd
```

명령을 실행하거나 재작성하지는 않는다. 정규화 결과는 차단 여부를 판단하는 입력일 뿐이며, deny 응답에는 정책 ID와 짧은 이유만 포함한다.

## 검증

- 일반 인용과 Bash ANSI-C 인용을 포함한 우회 사례 7개를 정책 회귀 테스트로 추가하고, 수정 전에는 해당 사례가 실패함을 확인했다.
- 수정 후 `.codex/hooks/tests` 전체 회귀 71개가 통과했다.
- 통합 검증에서는 일반 Hook 신뢰 모드의 Codex CLI에서 `git reset --h''ard`를 요청하고, 실행 전에 `[GIT_DESTRUCTIVE]` deny가 표시되는지 확인한다. 명령은 읽기 전용 샌드박스에서 실행해 Guard에 결함이 남아도 작업 트리를 보호한다.
- Logging Hook의 로컬 JSONL에 `PreToolUse` 이벤트가 기록됐는지 사람이 확인한다. 로그 파일은 Git에 포함하지 않으므로, 외부 문서나 PR 근거로 사용하기 전에는 결과를 재실행하고 검토한다.

## 한계와 운영 원칙

이 Guard는 완전한 보안 경계가 아니다. ANSI-C 인용과 `shlex` 토큰화는 변수 확장, 명령 치환, alias·함수, `eval`, 인코딩된 명령처럼 실행 시점에 만들어지는 내용을 해석하지 않는다. 이 범위는 Codex 샌드박스와 운영체제 권한, 정확한 대상 확인과 사람의 승인으로 분리해 통제한다.

새로운 우회 사례가 발견되면 먼저 재현 테스트를 추가한다. 테스트가 실패하는 것을 확인한 뒤 최소한의 정책 변경을 적용하고, 자동 회귀와 실제 `PreToolUse` 통합 검증을 다시 수행한다.

## 이력서와 포트폴리오 표현 후보

### 이력서

AI 코딩 도구의 위험 명령 실행 경로를 검증하면서 셸 인용으로 분할된 `git reset --hard` 옵션이 문자열 기반 Guard를 우회하는 사례를 재현했습니다. `PreToolUse` Guard를 토큰 정규화 방식으로 보완하고 71개 Hook 회귀 테스트로 정책 동작을 검증했습니다.

### 포트폴리오에서 설명할 핵심

AI 도구의 Hook은 실행 이력을 남기는 기능과 위험 명령을 차단하는 기능을 분리했습니다. 셸 인용 우회 표현이 정책 테스트에서 통과하는 문제를 재현하고, 원인을 셸 인자 결합과 원본 문자열 비교의 차이로 좁혔습니다. 실행하지 않는 토큰 정규화로 보완한 뒤 자동 회귀를 수행했으며, 실제 CLI 차단과 로컬 로그 확인은 사람이 재실행하는 통합 검증 절차로 분리했습니다. 이 통제는 샌드박스나 사람의 승인을 대체하지 않는다는 한계를 문서와 정책에 함께 남겼습니다.
