# DevChat 조회 API 실행 계획 분석 설계

## 목표

DevChat의 조회 경로 네 개를 동일한 MySQL 8.4 환경에서 가볍게 비교한다. 실제 SQL과 실행 계획을 근거로 병목 후보를 하나 선택한다. 후보가 확인된 경우에만 해당 경로를 개선하고 같은 조건으로 재측정한다.

이 작업의 목적은 특정 쿼리가 느리다고 미리 결론 내리는 것이 아니다. 데이터 증가에 따라 실행 계획이 어떻게 변하는지 확인하고, 수정할 가치가 있는 문제가 관측될 때만 운영 코드를 변경하는 것이다.

## 분석 대상

### 전체 알림 조회

- 본인이 구현한 `NotificationRepository.getNotifications`를 대상으로 한다.
- 수신자 조건으로 알림을 조회하는 select 쿼리와 `Page`가 생성하는 count 쿼리를 함께 분석한다.
- `NotificationDto` 변환 과정에서 지연 로딩된 발신자와 수신자를 접근하므로 추가 Member 조회가 발생하는지도 기록한다.

### 읽지 않은 알림 조회

- 본인이 구현한 `NotificationRepository.getNotReadNotification`을 대상으로 한다.
- 수신자와 읽음 여부를 함께 필터링할 때 현재 수신자 단일 인덱스가 어느 범위까지 사용되는지 확인한다.
- 읽지 않은 알림 비율에 따라 검사 행 수가 어떻게 달라지는지 비교한다.

### DM 메시지 이력 조회

- 기존 `DmMessageRepository.findMessagesByRoomId` 경로와 개선 후 `findMessageIdsByRoomId`, `findAllWithSenderByIdIn` 경로를 대상으로 한다.
- `room_id`로 필터링하고 `sent_at DESC`로 정렬하는 select 쿼리와 `Page` count 쿼리를 분석한다.
- 현재 `room_id` 단일 인덱스에서 별도 정렬이 발생하는지 확인한다.

### 단체채팅 메시지 이력 조회

- 팀원이 구현한 `ChatMessageRepository.findByChatRoom_IdOrderByIdDesc`와 `findByChatRoom_IdAndIdLessThanOrderByIdDesc`를 비교 기준으로 사용한다.
- 현재 적용된 `(room_id, message_id DESC)` 복합 인덱스와 커서 페이지네이션의 실행 계획을 기록한다.
- 이 경로의 기존 구현을 본인 성과로 주장하지 않는다. DM과 알림 조회 방식의 개선 대안을 평가하기 위한 기준선으로만 사용한다.

## 접근 방법

### 선택한 방법: SQL 우선 분석 후 하나의 API만 심화 검증

먼저 격리된 MySQL에서 네 조회 경로의 SQL 수준 특성을 비교한다. 이 단계에서는 인덱스와 애플리케이션 코드를 변경하지 않는다. 비교 결과 문제가 가장 선명한 한 경로를 선택한 뒤에만 Repository 또는 스키마를 수정하고 API 수준 부하 테스트를 수행한다.

이 방법을 선택한 이유는 API 전체를 먼저 부하 테스트하면 인증, Redis, 직렬화, 네트워크 같은 변수가 DB 원인과 섞이기 때문이다. 반대로 SQL 실행 시간만 측정하면 DTO 변환 중 추가 조회와 실제 API 응답 비용을 놓칠 수 있다. 따라서 SQL 분석으로 원인을 좁힌 뒤 선택된 경로만 API로 검증한다.

### 제외한 방법

- 네 경로를 모두 개선하지 않는다. 작업량이 커지고 결과가 얕아진다.
- 처음부터 커넥션 풀 크기를 변경하지 않는다. HikariCP 대기가 실제로 관측될 때만 별도 분석한다.
- 운영 데이터베이스와 홈서버 데이터는 사용하지 않는다. 모든 데이터는 격리된 로컬 MySQL에 생성한다.
- 단체채팅의 기존 복합 인덱스와 커서 페이지네이션을 본인 구현으로 표현하지 않는다.

## 실험 환경

- 데이터베이스는 프로젝트 운영 Compose와 같은 `mysql:8.4` 이미지를 사용한다.
- 실험용 Compose 프로젝트, 네트워크, 볼륨, 데이터베이스 이름은 기존 개발 및 운영 환경과 분리한다.
- 스키마는 `backend/src/main/resources/db/migration`의 Flyway 마이그레이션 V1부터 V5까지를 빈 데이터베이스에 순서대로 적용한다.
- 데이터 생성과 결과 수집은 `backend/perf/query-analysis` 아래의 재현 가능한 스크립트로 관리한다.
- 실험 스크립트는 명시적인 실험용 컨테이너 이름과 데이터베이스 이름을 검증한 뒤에만 데이터를 초기화할 수 있다.

## 1차 데이터셋

후보를 고르는 1차 분석에서는 두 단계의 관련 데이터 규모를 사용한다.

| 단계 | 대상 사용자 또는 방에 속한 행 수 | 목적 |
|---|---:|---|
| Small | 1,000 | 쿼리와 결과 정합성 확인 |
| Medium | 10,000 | 실행 계획 변화 확인 |

High(100,000행) 데이터셋은 1차 분석에서 후보가 확인된 경우에만 만든다. 개선 전후의 인덱스와 정렬 비용 차이를 검증하는 데 사용한다.

각 단계에서 대상 외 데이터도 함께 생성해 인덱스 선택도를 확인한다. 대상 외 데이터는 대상 행 수와 같은 수로 생성한다.

- 알림은 한 명의 대상 수신자에게 단계별 행 수를 생성하고, 다른 수신자에게 같은 수의 행을 생성한다.
- 대상 수신자의 읽지 않은 알림 비율은 20%로 고정한다.
- DM은 한 대상 방에 단계별 행 수를 생성하고, 다른 방들에 합계가 같은 행 수를 생성한다.
- 단체채팅도 한 대상 방에 단계별 행 수를 생성하고, 다른 방들에 합계가 같은 행 수를 생성한다.
- 모든 시간 컬럼은 중복 가능성을 포함해 일정 간격으로 생성한다. 결과 순서의 결정성을 확인할 때는 기본 키를 보조 정렬 후보로 검토한다.

## 측정 절차

각 1차 데이터 규모에서 다음 순서를 지킨다.

1. 데이터 개수와 분포를 SQL로 검증한다.
2. Repository가 생성하는 실제 select와 count SQL을 확보한다.
3. 각 SQL에 `EXPLAIN ANALYZE`를 실행한다.
4. 사용 인덱스, actual rows, loops, sort 또는 temporary table 여부와 실행 시간을 기록한다.
5. 첫 실행은 준비 실행으로 제외하고 같은 쿼리를 한 번 더 실행해 결과가 재현되는지 확인한다.
6. 알림 API는 한 페이지를 DTO로 변환할 때 실행되는 전체 SQL 수를 별도로 기록한다.
7. 단체채팅은 첫 페이지 조회와 깊은 커서 조회를 나누어 기록한다.

SQL 실행 시간은 절대적인 운영 성능으로 해석하지 않는다. 동일한 로컬 환경에서 데이터 규모와 쿼리 구조에 따른 상대 변화를 비교하는 근거로만 사용한다.

## 대상 선택 기준

다음 기준을 순서대로 적용해 심화 개선 대상을 하나 선택한다.

1. 본인이 구현한 알림 또는 DM 경로에서 재현 가능한 문제가 발견되었는가.
2. 데이터가 증가할수록 actual rows, 정렬 비용, 쿼리 수 또는 실행 시간이 유의미하게 증가하는가.
3. 실행 계획과 애플리케이션 흐름으로 원인을 설명할 수 있는가.
4. 개선 전후를 같은 조건에서 자동으로 재측정할 수 있는가.
5. 개선이 실제 조회 요구사항을 훼손하지 않는가.

알림과 DM 모두 문제가 없으면 억지로 운영 코드를 변경하지 않는다. 이 경우 분석 결과와 단체채팅의 기존 최적화 구조를 학습 기록으로 남기고 Track 1을 종료한다.

## 심화 분석과 개선 대안 평가

1차 분석에서 선택된 경로에 한해 High 데이터셋, 반복 측정, 아래 대안을 적용한다.

- 알림 조회: 복합 인덱스, fetch join 또는 DTO projection, `Page`에서 `Slice` 전환
- DM 조회: `(room_id, sent_at, id)` 계열 복합 인덱스, 결정적 정렬, 커서 페이지네이션, `Page`에서 `Slice` 전환
- 공통: 반환 결과 정합성, 페이지 경계 중복과 누락, count 제공 필요성

인덱스는 실행 계획에서 필요성이 확인된 경우에만 Flyway 마이그레이션으로 추가한다. 커서 페이지네이션은 프론트엔드 계약 변경 비용까지 포함해 평가한다. 단순히 더 빠르다는 이유만으로 API 응답 계약을 바꾸지 않는다.

## API 수준 검증

심화 대상을 선택하고 SQL 수준 개선 결과가 확인된 경우에만 동일한 데이터셋에서 API 부하 테스트를 수행한다. 1차 분석만으로는 API 부하 테스트를 하지 않는다.

- 동일한 인증 사용자와 동일한 페이지 크기를 사용한다.
- 개선 전후에 같은 요청 시나리오와 동시 사용자 수를 적용한다.
- p50, p95, p99, 처리량과 오류율을 기록한다.
- DB 커넥션 대기가 관측될 때만 Hikari active와 pending을 추가 기록한다.
- API 측정 결과가 SQL 분석과 다르면 애플리케이션 쿼리 수, 직렬화와 인증 비용을 다시 분리해 확인한다.

## 검증과 안전장치

- 데이터 초기화 명령은 실험용 데이터베이스 식별자가 일치하지 않으면 실패한다.
- 운영 및 공용 개발 데이터베이스 주소를 인자로 받을 수 없게 한다.
- 개선 전후 조회 결과의 개수와 순서를 자동 테스트로 비교한다.
- 페이지 경계에서 메시지 또는 알림의 중복과 누락이 없는지 검증한다.
- Flyway 변경이 생기면 빈 MySQL 8.4에서 전체 마이그레이션 테스트를 실행한다.
- 기존 단위 테스트와 관련 Repository 통합 테스트를 실행한다.

## 산출물

- 네 조회 경로의 실제 SQL 목록
- Small·Medium 데이터 규모별 `EXPLAIN ANALYZE` 원본
- 실행 계획 비교표
- 심화 대상 선택 근거
- 후보가 확인된 경우에만: 적용한 개선과 대안 비교, High 데이터셋의 개선 전후 결과, API 부하 결과
- 1차 분석 재현 명령과 환경 정리 명령

포트폴리오 문장은 개선 전후 결과가 확보된 뒤에만 작성한다. 측정 전에는 “병목 해결”, “성능 개선”, “커넥션 풀 경합 해결”이라고 표현하지 않는다.
